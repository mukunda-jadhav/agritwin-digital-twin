# MASTER PROMPT — AI-Powered Smart Farm Digital Twin

## Your Role

Act as a senior full-stack software architect, expert React and Three.js developer, Node.js backend engineer, agricultural simulation specialist, and machine learning engineer.

Build a complete, production-quality, full-stack web application called **AgriTwin — AI-Powered Smart Farm Digital Twin**.

This is a final-year BTech Computer Science Engineering project. The application must be visually impressive, technically sound, interactive, modular, and suitable for a live college project demonstration.

Do not build a simple farming dashboard or static 3D model. Build an actual working software-based digital twin where simulated farm conditions evolve over time based on weather, irrigation, soil properties, and crop growth.

## 5. Agricultural Simulation Engine

Build a dedicated deterministic simulation engine in TypeScript.

The simulation should advance using a virtual clock independent of actual wall-clock time.

Support:

- Pause
- Resume
- Advance one day
- Simulate multiple days
- Change simulation speed
- Reset
- Save simulation snapshots
- Replay historical simulation states

### Soil Moisture Simulation

Use a documented water-balance model based on:

- Initial soil moisture
- Rainfall
- Irrigation
- Evapotranspiration
- Soil water-holding capacity
- Drainage
- Crop water requirements

Maintain consistent units, such as millimeters of water per plot or millimeters of root-zone water depth.

A simplified conceptual relationship is:

New soil water = Previous soil water + Effective rainfall + Irrigation − Crop evapotranspiration − Drainage

Clamp values to physically valid soil-water limits.

Clearly document assumptions and limitations.

### Crop Growth Simulation

Use a simplified crop-growth model considering:

- Growing Degree Days
- Crop age
- Temperature
- Soil water availability
- Growth stages
- Water stress

Growth stages should include:

- Germination
- Vegetative growth
- Flowering
- Fruit development
- Maturity
- Harvest

Use research-supported parameters for the initial tomato crop where available.

Do not claim that the simulation accurately predicts real farm outcomes without validation.

## 6. Open-Meteo Weather Integration

Integrate Open-Meteo through the Express backend.

Features:

- Fetch weather using farm coordinates
- Display current weather and forecast
- Retrieve historical weather when needed
- Cache responses
- Store weather snapshots used by simulations
- Use actual weather data as inputs to the farm simulation
- Provide fallback sample weather data for offline demonstrations

Distinguish observed historical weather, forecast weather, and synthetic future weather.

For simulations extending beyond the available forecast horizon, use explicitly labeled synthetic weather scenarios rather than pretending actual forecasts exist.

Ensure the application can reproduce previous simulations using the same saved weather inputs.

## 7. AI and Machine Learning with TensorFlow.js

Create a separate ML module inside the Node.js application.

### Model A — Irrigation Recommendation

Inputs may include:

- Soil moisture
- Soil type
- Crop growth stage
- Temperature
- Forecast rainfall
- Estimated evapotranspiration
- Recent irrigation history

Output:

- Whether irrigation is recommended
- Suggested water amount
- Estimated timing

Start with a deterministic agronomic baseline, then develop a TensorFlow.js model using suitable labeled data.

### Model B — Crop Stress Prediction

Inputs:

- Soil moisture
- Temperature
- Crop stage
- Water deficit
- Recent weather

Outputs:

- Low stress
- Moderate stress
- High stress

### Model C — Yield Estimation

Inputs:

- Crop growth progress
- Accumulated temperature
- Water stress history
- Weather conditions
- Crop-specific parameters

Output:

- Estimated yield
- Prediction range where justified
- Factors affecting the prediction

Use appropriate public agricultural datasets where available.

Create separate scripts for training and evaluation. Record dataset provenance, preprocessing, train/test splits, evaluation metrics, and limitations.

Avoid training and evaluating on the same simulated records or leaking future information into training features.

If credible training data is unavailable, implement and label a transparent simulation-based baseline instead of inventing ML accuracy.

Persist trained models and load them for backend inference. Keep training outside normal HTTP request processing.

## 9. What-If Scenario Simulator

This is one of the most important features.

Allow users to test questions such as:

- What if I stop irrigation for seven days?
- What if rainfall decreases by 30%?
- What if I irrigate every two days?
- What if the temperature rises by 4°C?
- What if I reduce water usage by 25%?

Users should be able to clone the current farm simulation state, modify parameters, and compare results.

Compare:

- Soil moisture
- Crop stress
- Growth progress
- Water consumption
- Estimated yield

Ensure scenario comparisons use the same starting conditions and weather inputs unless the scenario intentionally changes weather.

Display side-by-side charts and summary metrics.

Never overwrite the original simulation when running an experiment.

## 10. Real-Time Updates with Socket.IO

Use Socket.IO for simulation events.

Suggested events:

- simulation:started
- simulation:paused
- simulation:ticked
- farm:state-updated
- irrigation:applied
- crop:growth-updated
- prediction:updated
- simulation:completed

The backend must remain authoritative for simulation state.

The frontend should receive synchronized updates without independently calculating authoritative farm values.

Use authenticated farm-specific Socket.IO rooms.

Support reconnecting clients by fetching the latest authoritative state.

## 12. Database Architecture

Design a normalized Prisma schema containing:

- User
- Farm
- Plot
- Crop
- Planting
- WeatherRecord
- SimulationRun
- SimulationSnapshot
- PlotState
- IrrigationEvent
- Prediction
- Scenario

Use foreign keys, indexes, timestamps, and appropriate constraints.

Store farm ownership and ensure users cannot access another user's data.

Use database transactions where multiple related simulation updates must be persisted atomically.

Avoid saving unnecessary high-frequency duplicates. Store periodic snapshots and meaningful events for efficient replay and analytics.
